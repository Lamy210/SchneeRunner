# SchneeRunner v0.1.0 Bootstrap Release Design

## Context

SchneeRunner has a two-stage macOS release pipeline that is designed around a stable SemVer tag push:

1. `Release Build` runs on `vX.Y.Z` tag pushes and builds/tests the unsigned app without release credentials.
2. `Release Publisher` validates the exact upstream run/artifact, then publishes an unsigned DMG through the reusable release workflow.

Unsigned publication is now supported intentionally: Developer ID signing and notarization are skipped while DMG structure, executable payload, checksum, provenance, source/tag binding, and immutable GitHub Release publication remain enforced.

The current repository has no tags and no GitHub Releases. Because no `v0.1.0` tag exists, `Release Build` has never been triggered.

The ChatGPT GitHub connector used for this development session can create branches, files, PRs, and merges, but it does not expose a tag-ref creation mutation. A workflow that creates a tag with its repository `GITHUB_TOKEN` also cannot rely on that tag push to recursively trigger the existing tag-push workflow. Therefore the first release needs a bootstrap path that performs the first release directly from trusted `main` while preserving the existing normal tag-based path for later releases.

## Goal

Publish SchneeRunner `v0.1.0` as an easy-to-download GitHub Release without Developer ID signing/notarization, and create the matching `v0.1.0` tag pointing to the exact trusted source commit.

Success means:

- a lightweight `v0.1.0` tag points to the exact `main` commit being released;
- GitHub Releases contains a non-draft, non-prerelease `v0.1.0` release;
- the release contains `SchneeRunner-0.1.0.dmg`, its SHA-256 checksum, and provenance metadata;
- the DMG contains an executable `SchneeRunner.app` built from the tagged source;
- the release is intentionally unsigned and unnotarized;
- README gives users an obvious `Download latest release` path and explains the unsigned macOS launch caveat;
- normal future releases continue to use the existing tag-driven `Release Build -> Release Publisher` pipeline.

## Non-goals

This bootstrap does not:

- add Developer ID signing;
- add notarization;
- redesign the application build system;
- weaken the existing normal tag-driven release validation contract;
- make every merge to `main` a release;
- introduce a permanent second release pipeline for future versions.

## Chosen approach

Add a narrowly scoped, one-time bootstrap workflow for `v0.1.0` that runs only from trusted `main` after the workflow itself is merged.

The workflow will be idempotent and fail closed:

1. Require `github.ref == refs/heads/main` and require the repository identity to be `Lamy210/SchneeRunner`.
2. Query the repository and stop successfully if both the `v0.1.0` tag and its immutable release already exist with the expected assets.
3. Refuse to proceed if `v0.1.0` exists but points somewhere other than the current trusted source SHA.
4. Build/test the unsigned app using the existing `scripts/ci/build-release-artifact.sh` with version `0.1.0`.
5. Package and structurally validate the app using the existing release helper scripts.
6. Create `SchneeRunner-0.1.0.dmg` using the existing DMG builder.
7. Verify the unsigned DMG with `RELEASE_SIGNED=false` using `scripts/release/verify-release.sh`.
8. Produce canonical SHA-256 output and bootstrap release provenance bound to repository, source SHA, version, and workflow run identity.
9. Create lightweight tag `refs/tags/v0.1.0` at the exact source SHA using GitHub's API with `contents: write`.
10. Re-resolve the tag and verify that it still points to the source SHA before publication.
11. Create the GitHub Release with the DMG, checksum, and provenance metadata; if a concurrent release already exists, verify exact asset identity instead of replacing it.
12. Re-verify tag binding and remote release assets after publication.

The workflow will use the repository `release` environment only if an existing publication policy requires it; it will not receive Apple signing/notarization secrets.

## Why not rely on a tag created by the bootstrap to trigger Release Build

GitHub prevents recursive workflow chains from most events created with the repository `GITHUB_TOKEN`. A tag created by a workflow therefore must not be assumed to trigger the existing `push.tags` release workflow.

The bootstrap performs the first release in the same run instead of depending on a second implicit workflow trigger.

## Why not redesign Release Build around workflow_dispatch now

Adding a reusable/manual dispatch path would require broadening the provenance contract, source-event validation, tag/source/ref semantics, and publisher assumptions that currently deliberately require a successful tag `push` run. That is useful future work but larger than necessary to publish the first release.

The bootstrap is intentionally disposable. After `v0.1.0` is published and verified, future releases should use the existing tag-driven pipeline.

## Files and responsibilities

### `.github/workflows/bootstrap-v0.1.0-release.yml`

One-time trusted-main workflow. Owns build/test, tag creation, unsigned DMG production, release publication, and final remote verification for `v0.1.0` only.

It must use pinned action SHAs, minimal permissions, explicit repository/ref checks, concurrency protection, and exact asset-name validation consistent with the existing release workflows.

### `scripts/release/*`

Reuse existing scripts wherever possible. Add only a small bootstrap provenance helper if the existing final provenance schema cannot honestly represent a release that does not pass through the normal validated-artifact publisher stages.

Do not fabricate normal publisher artifact IDs/digests. Bootstrap provenance must identify itself as bootstrap provenance rather than pretending to be a normal `Release Publisher` run.

### `scripts/release/test_*`

Add contract tests covering:

- workflow is restricted to `main` and exact `v0.1.0`;
- workflow creates a tag only at the current source SHA;
- unsigned verification is required;
- signing/notarization steps are absent;
- DMG/checksum/provenance assets are required;
- existing mismatched tag/release state fails closed;
- a matching existing release is idempotent/no-op;
- README exposes a stable download path.

Tests must fail before production workflow changes and pass afterward.

### `README.md`

Add a prominent download section near the top:

- `Download latest release` linking to the repository's `/releases/latest` page;
- supported platform: macOS 14+;
- installation: download DMG, open it, move SchneeRunner to Applications;
- unsigned warning: macOS may block first launch because the app has no Developer ID signature/notarization;
- concise launch guidance that does not imply the app is signed or Gatekeeper-approved.

Do not link directly to a versioned asset from the README because `/releases/latest` should remain stable across future versions.

## Tag policy

The bootstrap creates a lightweight `v0.1.0` tag at the exact source commit used for the release.

Before creating it:

- if no `v0.1.0` tag exists, creation is allowed;
- if it exists and resolves to the exact source SHA, creation becomes a no-op;
- if it exists and resolves elsewhere, the workflow fails and does not publish or overwrite anything.

After creating it, the workflow re-fetches the ref and verifies the exact SHA before publication and again after publication.

The tag must never be force-moved by the bootstrap.

## Release publication contract

Expected release assets are exactly:

- `SchneeRunner-0.1.0.dmg`
- `SchneeRunner-0.1.0.dmg.sha256`
- `release-provenance.json`

The release is:

- title: `v0.1.0`;
- tag: `v0.1.0`;
- draft: false;
- prerelease: false;
- generated release notes allowed;
- unsigned/unnotarized by design.

If `v0.1.0` already exists, the workflow must download and hash its assets and only accept a byte-identical release. It must not replace immutable assets.

## Security model

The bootstrap is trusted-control-code execution from `main`, not untrusted tag-selected code.

Required controls:

- exact repository identity check;
- exact `main` ref check;
- no PR/fork execution path;
- minimal `contents: write` only where tag/release publication is required;
- no Apple credentials;
- pinned third-party actions;
- no scripts taken from downloaded artifacts;
- explicit release filename validation;
- exact tag/SHA binding before and after publication;
- checksum verification of local and downloaded remote DMG;
- concurrency group preventing two bootstrap publishers from racing.

Because the app is unsigned, the workflow must not run `codesign`, Gatekeeper acceptance checks, stapler, or notarization as success requirements. Structural/executable/DMG/checksum verification remains mandatory.

## Lifecycle

This workflow exists to publish the first stable release. Once `v0.1.0` is confirmed remotely, it should either:

- remain permanently inert because it is hard-coded/idempotent for `v0.1.0`; or
- be removed in a later cleanup PR.

It must not be generalized implicitly into the normal release path.

Future releases (`v0.1.1`, `v0.2.0`, etc.) continue through the existing stable tag push pipeline.

## Verification

Before merge:

- RED contract tests demonstrate the current repository cannot bootstrap `v0.1.0`;
- GREEN contract tests verify the bootstrap workflow and README contract;
- normal `Tests`, `Swift Quality`, `Quality`, `Release Isolation TDD`, and `SchneeRunner CI` gates all pass;
- workflow security/lint checks pass;
- no unresolved review findings remain.

After merge:

- bootstrap workflow completes successfully on the merge commit;
- `refs/tags/v0.1.0` resolves to that exact source SHA;
- GitHub Release `v0.1.0` exists and is public;
- all three expected assets are present;
- downloaded DMG hash equals its published checksum;
- README latest-release link resolves to the new release.
